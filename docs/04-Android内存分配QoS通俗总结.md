# 这次的 Android 内存分配 QoS 改了什么

我把 `memory-QoS` 回到原始的 `6.1.124-android14-11-g8769cc47188c`，然后在这个版本上重新实现。实验默认关闭，平时系统继续按原来的方式分配内存。

## 有什么变化

当应用申请一页内存时，内核仍先照常尝试。如果一次就拿到了，马上交付。有实验资格、第一次没拿到的请求，可以向一个提前备好少量物理页的池子要页。

当两个已登记的应用都在排队时，实验可以设置成 3∶1。只要两边一直都有请求，而且持续有合格的页，内核就按“前台、前台、前台、后台”授权。内核先把具体的页绑定给相应的请求，再通知对应线程醒来。即使另一个线程更早恢复运行，它拿到的也是分给自己的页。只剩一边排队时，它可以继续用池里的页。

以计划里的 32 页为例，每页 4 KiB，预留的数据页合计 **128 KiB**。池子一时空了，排队请求超过等待预算就回到原来的分配方式，让原来的慢路径继续处理。后台的保障是每轮有一次获得池页的机会，实际完成时间还取决于有没有页，以及线程什么时候能恢复运行。

## 怎样看出哪一部分有用

| 对照 | 开启的功能 | 可以看什么 |
|---|---|---|
| N | 原生分配 | 原来的时延和吞吐 |
| P | 备页池 | 提前备页有没有帮助 |
| F | 备页池，按先来后到排队 | 排队等待和定向给页的整体效果 |
| W1 / W3 | 备页池，按 1∶1 或 3∶1 给页 | 增加前台份额后，前台和后台分别有什么变化 |

## 已经验证到哪一步

Pixel 7 的实验镜像已经构建。ARM64 虚拟机用镜像里的同一份内核验证了给页顺序、两边异序领取、没页时继续保留轮转位置、超时回退、撤销授权，以及停机后页和请求都能对账。匿名缺页的入口也已跑通，测试进程能正常拿到清零后的页。

Pixel 7 真机上的收益还没有测出来。接下来需要用原来的 A/B 压力包，确认前台和后台确实都遇到了进入这个机制的慢请求。之后才能比较前台最慢的一批请求缩短了多少，以及后台完成率和总吞吐有没有变化。[实现交接](03-Android内存分配QoS实现交接.md)
